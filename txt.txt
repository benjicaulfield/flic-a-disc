# Deck Rewrite — TODO & Decisions

The big-picture architecture: one shell (`Deck`, formerly `Catalog`) that holds only
`activeId` and renders every tab mounted-but-visibility-toggled (for state persistence).
Each tab is a self-contained module owning its own data lifecycle. Sources (Discogs, eBay,
…) are pluggable; parsing/normalization happens at the source boundary (backend for eBay,
since TF-IDF + enrichment already live in Django).

---

## 0. Conventions to lock in FIRST (so the next agent run doesn't re-smear things)

- [ ] Add **Biome** (`biome.json`) or stick with Prettier+ESLint. Biome = one tool,

## 5. Data model decisions (TYPES) — the cleanup

### Discogs
- [ ] **`DiscogsBySellerListing` is a divergent hand-copied duplicate of `DiscogsRecord`**
      (conflicts: `suggested_price` is `string` on Record but `number|null` here; missing
      `id`; adds `catno`/`score`/`price`/`currency`; drops `wanted`/`evaluated`/etc.).
      Since you're rewriting: don't recreate it. Use the nested pattern you already have
      in `DiscogsListing` = `{ ...saleFields, record: DiscogsRecord }`.
- [ ] Make keepers AND by-seller endpoints return the SAME nested shape. One type
      (`DiscogsListing`), one column set, one access pattern (`row.record.artist`).
      Add `score` only if by-seller genuinely provides it (extend, don't fork).
- [ ] **Resolve `suggested_price: string` on `DiscogsRecord`.** It's a string only
      because the API hands it over unparsed. Pick ONE type everywhere. Parse at the
      source boundary so the TS type is `number | null`.
- [ ] `grep -rn "DiscogsBySellerListing" src/` before deleting, to see blast radius.

### eBay — model + types
- [ ] **Reconcile model ↔ TS drift.** The Django model and the old TS `EbayListing`
      disagree:
      - `album` (model) vs `album_title` (TS)
      - `record_condition` (model) — TS missing `sleeve_condition`
      - `genre`/`style` singular (model) vs `genres`/`styles` plural (TS)
      - `keeper` (model) vs `saved` (TS) — confirm same concept or not
      - `ebay_id`: CharField→string (model) vs `number` (TS) — fix TS
      - `bid_count`: IntegerField→number (model) vs `string` (TS) — fix TS
      - model lacks `seller_name`/`created_at`/`updated_at` that TS had
- [ ] **Regenerate the TS eBay type from actual serializer output**, not the stale
      interface. Hit the endpoint, type against the JSON. (Optional: `drf-spectacular`
      → OpenAPI → generated TS, if drift becomes chronic.)
- [ ] Pick canonical field names and apply on BOTH sides (model wins unless renaming).

### eBay — lifecycle / persistence model
- [ ] **DECISION NEEDED: enrich-on-pass vs save-then-enrich-async.**
      - You confirmed: sub-TF-IDF listings are NEVER saved (gate is filter-before-insert,
        not a stored state). Good — removes the "scored but rejected" cluster.
      - Remaining fork:
        - **Enrich immediately on pass** → DB holds only fully-enriched rows. ONE state.
          TS metadata fields non-optional (`artist: string`). `BasicEbayListing`/
          `BasicEbayAuction` are scraper-internal Python shapes only — no DB rows, no TS
          types needed. Simpler. **Recommended for a personal tool.**
          - Caveat: scraping becomes synchronous with the expensive enrichment API call
            (run time ≈ passes × API latency). Fine for small batches; painful for large.
        - **Save-on-pass, enrich later (batched/async)** → two persisted states. Add an
          explicit `enriched = BooleanField(default=False)` so stage is a filterable
          field, not inferred from empty metadata. Store `tfidf_score`. TS metadata
          becomes optional. Better throughput.
      - [ ] Decide based on batch size / API latency. Lean enrich-on-pass unless scrape
            volume forces async.
- [ ] If enrich-on-pass: consider dropping `blank=True` on enriched metadata fields (or
      keep as defensive slack for fields the enrichment API sometimes omits).
- [ ] Clarify `keeper`/`evaluated` are POST-save user-decision flags (looked-at /
      want-it), not pipeline-stage flags.

### eBay — string-typed numerics
- [ ] **DECISION NEEDED: do you ever compute on price, or only display?**
      - Display-only → leave `price`/`current_bid` as `CharField`→string→render. Simplest,
        honest. No parsing.
      - Sort/filter by price → parse at SAVE into `DecimalField` (and `year`→nullable
        `IntegerField`) so sorting works server-side. Then TS says `price: number`.
- [ ] Whatever you choose: eBay parsing STAYS in Django (TF-IDF + enrichment already
      there; don't split one logical pipeline across two languages). Frontend receives
      finished typed rows; columns NEVER parse.
- [ ] Defensive parsing note: scraped `price` may be `"Best offer"`/empty. If you move to
      `DecimalField`, parse-and-null-on-failure (don't let a bad scrape throw). Optionally
      keep raw text field + typed field.

### eBay — `BasicEbayBuyItNow` vs `BasicEbayAuction` inconsistency
- [ ] One NESTS (`listing: BasicEbayListing`), the other is FLAT. Make consistent or
      you'll have two access patterns (`row.listing.ebay_title` vs `row.ebay_title`) in
      sibling tabs.

### eBay — genre/style cardinality
- [ ] Decide: is eBay genuinely single-genre (scrape only yields one) → singular
      `CharField` is honest. Or multi → comma-joined string vs real relation. Don't force
      it to match Discogs's `string[]` if the data doesn't support it.

## 6. Columns

- [ ] **No shared `baseColumns` across sources** — Discogs and eBay have different field
      TYPES for "same" columns (`year: number` vs `string`, `genres: string[]` vs
      `string`). A shared column's `cell` can't render both. So:
      - One column array PER row type: `discogsColumns`, `ebayColumns`, `sellerColumns`.
      - `ColumnDef<T>` is bound to one `T`; you can't mix a `ColumnDef<EbayListing>` into
        a `ColumnDef<DiscogsListing>` table.
- [ ] **Co-locate each column array in its tab file** (they're not reused). EXCEPTION: if
      Browse and Train both show the same Discogs columns, extract `discogsColumns` to a
      shared spot for those two.
- [ ] Fix the old type bug: columns were typed `ColumnDef<CatalogRecord>` but
      `CatalogRecord` doesn't exist / you import `DiscogsRecord`. Type against the real
      row type.
- [ ] Add small render helpers (live with each source's columns):
      - `joinList(v)` → guard with `Array.isArray(v)`, not `?? []` (defensive against a
        single string from a flaky source).
      - `money(v)` → handle null/undefined uniformly. (Old `price` cell did
        `getValue<number>()?.toFixed(2)` → renders `"$undefined"` when null, because `$`
        is outside the optional chain. Fix.)
- [ ] eBay columns: if numerics stay strings, `cell` parses string→number before format;
      put `parseMoney` etc. with the eBay columns.

## 8. Fetch / data layer (`sources/`)

- [ ] Each source module exports typed fetch fns:
      `fetchKeepers(): Promise<DiscogsListing[]>`, `fetchEbayBuyItNow(): Promise<EbayListing[]>`,
      etc. Parsing/normalization done INSIDE (for non-eBay; eBay is already clean from
      Django). Tabs get clean typed arrays, never raw JSON.
- [ ] **`apiFetch` returns the raw `Response` and does NOT check `res.ok`.** Every caller
      must: check `res.ok` (fetch only rejects on network failure — a 500 still resolves),
      `await res.json()`, AND have error handling. Old code calls `res.json()` with no
      `ok` check → on error, `data.records` is `undefined` → state set to garbage.
- [ ] Match the real backend pattern you use: `if (response.ok) { ... } else
      { setError(...) }`, with a `catch` for network/parse errors and a `finally` that
      ALWAYS does `setLoading(false)` (else a failed fetch spins forever).
- [ ] Endpoints are under `/api/discogs/...` (keepers = `/api/discogs/keepers`) — not the
      invented `/api/catalog/...`.
- [ ] `apiFetch` strips a leading `/`, so `'api/x'` and `'/api/x'` both work — not
      load-bearing. It also forces `credentials: 'include'`; since `options` spreads AFTER
      it, a caller could override `credentials` (fine, just know precedence).

## 10. Per-tab data lifecycle (persistence + lazy fetch)

- [ ] Because ALL tabs are mounted at once (for persistence), a naive
      `useEffect(..., [page])` in each fires every fetch on initial load — including the
      eBay scrape trigger, which must NOT fire just because the user landed on Deck.
- [ ] Gate each tab's fetch behind an "activated once" signal derived from `isActive`:
      ```ts
      function useActivated(isActive: boolean) {
        const [activated, setActivated] = useState(isActive);
        useEffect(() => { if (isActive) setActivated(true); }, [isActive]);
        return activated; // true once first shown, stays true
      }
      ```
      Don't fetch until `activated`. BulkGrading / eBay especially must not auto-run.
- [ ] Add a `cancelled` flag in fetch effects so a stale response from a rapid
      tab/page switch can't overwrite a newer one.
- [ ] BulkGrading is the odd tab: it's a RULE EDITOR (`1967 & Blue Note → keeper`), not a
      record table. Don't force it into the table abstraction. It writes to a
      `grading_rules` endpoint.
- [ ] Cross-tab shared state (e.g. grading rules that Train/annotation must read) does NOT
      live in a single tab — lift to a small context/store at the Deck level, or refetch
      server-side where applied. Keep per-tab UI state local; promote genuinely shared
      domain state up. Don't hoist everything back to the shell.
