# Bulk Grading Tool — Build Checklist

A bulk update tool: the four fields (artist, label, genre, style) define **which records to match** (a `WHERE` clause), and the yes/no toggle defines **the value to set** (a `SET`). Built database-outward, so the dangerous part is proven in isolation before a form can trigger it.

---

## Phase 0 — Decisions and recon (no building yet)
- [x] Confirm your stack: which database (Postgres, MySQL, SQLite?), and what backend you'll write the API in.
- [x] Open the database and look at the actual `records` table — note the exact column names and types for artist, label, genre, style, and the `wanted` column.
- [x] Decide the matching rule per field: exact, case-insensitive, or "contains." Write your decision down; everything downstream depends on it.
- [x] Make a throwaway copy of the data (or a test table) to experiment against. Do not learn this on the real table.

## Phase 1 — The update query, by hand

- [x] Write a single SQL `UPDATE` by hand for one hardcoded case (artist = Led Zeppelin, set wanted = false) and run it against your test copy.
WITH updated AS (
    UPDATE discogs_record_scratch SET wanted = false
    WHERE artist ILIKE '%led zeppelin%'
    RETURNING id
  )
  SELECT COUNT(*) FROM updated;
- [x] Verify it changed the rows you expected and nothing else.
- [x] Write the matching `SELECT COUNT(*)` version of the same filter — this is your future "preview." Confirm the count matches how many rows the update touched.

WITH updated AS (
    UPDATE discogs_record_scratch SET wanted = $5
    WHERE
      ($1 = '' OR artist ILIKE $1)
      AND ($2 = '' OR label  ILIKE $2)
      AND ($3 = '' OR $3 = ANY(genres))
      AND ($4 = '' OR $4 = ANY(styles))
    RETURNING id
  )
  SELECT COUNT(*) FROM updated;

- [x] Rewrite both queries using parameters (placeholders) instead of pasting values into the string. Look up "parameterized queries" for your database. Run them again to confirm they still work.

## Phase 2 — Building the filter dynamically
- [x] Sketch on paper how a partial form (only artist filled, others blank) should become a `WHERE` clause with only one condition.
- [x] Write a backend function that takes the four criteria and returns (a) the `WHERE` fragment and (b) the list of parameter values, including *only* the fields that are non-empty.
- [x] Test that function with several inputs: one field, three fields, all four.
- [x] **Critical:** make it reject the all-empty case. An empty filter matches every row — submitting a blank form must never be allowed to rewrite the whole table.

## Phase 3 — The API endpoints
- [ ] Stand up a backend that can receive a POST request and read a JSON body.
- [ ] Build a `preview` endpoint: takes criteria, runs the COUNT query, returns the number of matching rows.
- [ ] Build an `apply` endpoint: takes criteria *and* the yes/no value, runs the UPDATE, returns the number of rows changed.
- [ ] Test both with a tool like curl or Postman before any frontend exists — send fake payloads and watch the test table.

## Phase 4 — The frontend, wired up
- [ ] Take your existing form and on submit, call the `preview` endpoint instead of doing anything destructive.
- [ ] Show the user the returned count in plain language ("This will set 47 records to Not Wanted").
- [ ] Add a confirmation step — a second button or dialog — that only then calls the `apply` endpoint.
- [ ] On success, show the rows-affected count. On error, show a readable message.
- [ ] Add loading/disabled states so the user can't double-submit a bulk operation.

## Phase 5 — Hardening
- [ ] Re-test the empty-criteria guard end to end, from the form, not just the function.
- [ ] Confirm the toggle's yes/no maps to the correct `wanted` value (easy to invert by accident).
- [ ] Decide whether you need an undo or an audit log of what each bulk operation changed.
- [ ] Only when all of the above passes on the test copy, point it at the real database.

---

**Why this order:** by the time the form can do anything dangerous, you'll have already proven the query, the parameterization, the dynamic filter, and the empty-criteria guard each work on their own. Bugs stay isolated to the layer you just added.

# Seller Session — Build Checklist

Adapt DiscogsSellerBrowse into a full annotation session: fetch a seller's inventory, enrich it, auto-reject below the demand floor, score the rest, annotate, and save the session.

Base: DiscogsSellerBrowse.tsx + ML seller_browse view (already fetches wants/haves/suggested_price/score).

---

## Phase 1 — Enrichment and demand floor (backend / ML service)

- [ ] In `seller_browse` view: after scoring, compute demand = wants / (wants + haves) for each listing (guard against divide-by-zero).
- [ ] Accept a `demand_floor` query param (default e.g. 0.4). Auto-mark any listing below the floor: set `evaluated=True, wanted=False` in the Record table if a matching record exists.
- [ ] For listings at or above the floor with wants > haves and no suggested_price: fetch suggested prices (already have EnrichRecords — wire it in here).
- [ ] Re-score remaining listings: combined_score = (demand_weight × demand) + (price_weight × (suggested_price − listing_price) / suggested_price). Use configurable weights (default 0.6 / 0.4).
- [ ] Sort final list by combined_score descending.
- [ ] Return: full listing data + `demand`, `combined_score`, `auto_rejected_count`, `demand_floor` used.

## Phase 2 — SellerSession model

- [ ] Add `SellerSession` Django model: `seller_name`, `demand_floor`, `total_listings`, `auto_rejected`, `annotated_wanted`, `annotated_unwanted`, `created_at`.
- [ ] Add `SellerSessionListing` join model or JSON field: one row per listing with `discogs_id`, `wanted` annotation, `combined_score`.
- [ ] Run migration.
- [ ] Add `POST /ml/discogs/seller/session/` endpoint: accepts session data + annotation labels, saves to DB.
- [ ] Wire through Go: `POST /api/discogs/seller/session` → proxy to ML service.

## Phase 3 — Frontend (DiscogsSellerBrowse.tsx)

- [ ] Add `demandFloor` input (slider or number field, default 0.4) next to the seller input.
- [ ] On fetch response: separate auto-rejected listings from the annotatable list; show auto-rejected count as a badge ("X auto-rejected below floor").
- [ ] Add WANTLIST checkbox column to the table (same pattern as Catalog train tab).
- [ ] Show `demand` and `combined_score` columns; hide raw `score`.
- [ ] Add SUBMIT button bottom-right: disabled until at least one checkbox is touched.
- [ ] On submit: POST session payload (seller, demand_floor, all listing IDs + wanted values) to `/api/discogs/seller/session`.
- [ ] Show confirmation: "Session saved — N wanted, M unwanted, K auto-rejected."
- [ ] Clear checkboxes and allow re-fetch for a new seller.

## Phase 4 — Hardening

- [ ] Guard: if `wants` or `haves` are 0 (unenriched), skip demand calculation and include listing as-is (don't auto-reject unenriched records).
- [ ] Confirm auto-rejected records are written to DB before response, not fire-and-forget.
- [ ] Add loading state during the (slow) fetch — seller inventory can take 30s+.
- [ ] Test with a seller that has no NM/VG+ listings (empty result after condition filter).
